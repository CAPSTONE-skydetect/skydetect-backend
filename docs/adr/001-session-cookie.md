# ADR 001. 세션 쿠키 기반 인증

- 상태: 채택
- 일자: 2026-09-12

## 배경

SkyDetect 백엔드는 시설관리자가 관제 화면에서 실시간 영상을 보고, 비행물체를
발견하면 해당 구간을 잘라 분석을 요청하는 시스템이다. 이 시스템에 접근 제어를
도입하려면 인증 방식을 먼저 정해야 한다.

인증 방식 선택에 영향을 주는 조건은 다음과 같다.

| 조건 | 현재 상태 |
| --- | --- |
| 인증이 필요한 주체 | 시설관리자 한 종류 |
| 클라이언트 | 웹 브라우저 하나 (모바일 앱 없음) |
| 인증 서버 인스턴스 | Spring 1대 (로드밸런싱 없음) |
| 외부 공개 API | 없음 |
| 세션 지속 성격 | 관제실 상주. 장시간 로그인 유지 |

AI 파이프라인(FastAPI)은 별도 프로세스이지만 인증을 수행하지 않고 세션도 갖지
않는다. 사람이 접근하는 진입점은 Spring 하나뿐이므로, 세션을 공유해야 할 대상도
Spring 하나다.

### 용어 정리

"세션이냐 쿠키냐"는 잘못된 대립이다. 둘은 층위가 다르다.

- **쿠키** — 브라우저가 요청에 자동으로 실어 보내는 전달 수단
- **세션** — 서버가 사용자 상태를 보관하는 저장 방식

세션 방식은 쿠키를 도구로 써서 세션 ID만 전달하고, 실제 정보는 서버에 둔다.
실제 선택축은 두 개이며 서로 독립적이다.

| | 쿠키로 전달 | 헤더로 전달 |
| --- | --- | --- |
| 서버가 상태 보관 (세션) | **본 문서의 선택** | 가능 (드묾) |
| 토큰에 상태를 담음 (JWT) | 가능 (흔함) | 가장 흔한 JWT 구성 |

## 결정

**세션 쿠키(`JSESSIONID`) 기반 인증을 채택한다. JWT를 사용하지 않는다.**

세부 사항:

- 쿠키 속성: `HttpOnly`, `SameSite=Lax`. `Secure`는 HTTPS 환경에서만 부여
- 로그인 응답은 JSON 형식으로 한다
  - 성공 → `200` + JSON 바디
  - 실패 → `401` + 에러 JSON
  - 미인증 접근 → `401`. 로그인 페이지로 리다이렉트하지 않는다
- 역할은 `ROLE_OPERATOR` 단일로 시작한다
- 세션 만료 정책

  | 종류 | 뜻 | 설정값 |
  | --- | --- | --- |
  | 유휴 만료 | 마지막 요청 후 N분 무활동 시 만료. 요청이 오면 갱신 | 30분 |
  | 절대 만료 | 로그인 시각 기준 N시간이면 활동과 무관하게 만료 | 12시간 |
  | remember-me | 장기 로그인 유지 쿠키 | 미사용 |

- AI 파이프라인에는 인증을 두지 않는다. 네트워크 격리(루프백 바인딩 또는
  방화벽/보안그룹)로 외부 접근을 차단한다

## 근거

### 1. JWT의 장점이 이 시스템에서 성립하지 않는다

JWT가 유리해지는 대표 조건은 수평 확장, 다중 클라이언트, 외부 API 공개다.
배경의 조건표에서 보듯 셋 다 해당하지 않는다. 서버는 1대이고, 클라이언트는
브라우저 하나이며, 외부에 공개하는 API가 없다.

### 2. 즉시 로그아웃이 필요하다

관제 시스템 특성상 계정을 즉시 차단해야 하는 상황이 생길 수 있다. JWT는 한 번
발급한 토큰을 만료 전에 무효화할 수단이 없다. 세션은 서버가 저장소에서 지우면
그 즉시 무효가 된다.

### 3. 두 방식의 한계는 대칭이 아니다 (가장 강한 근거)

- 세션의 한계는 확장성이다. 서버가 늘어나면 세션 공유가 필요해지는데, Redis 등
  외부 세션 저장소로 보완할 수 있고 **보완해도 여전히 세션 방식이다.** 설계가
  뒤집히지 않는다.
- JWT의 한계는 무효화 불가다. 블랙리스트로 보완할 수 있지만, 그 순간 서버가
  상태를 갖게 되어 **무상태성을 잃는다. JWT를 선택한 이유 자체가 사라진다.**

즉 한쪽은 보완해도 원래 설계가 유지되고, 다른 쪽은 보완하면 설계가 자기모순에
빠진다. 되돌리기 비용이 비대칭이다.

### 4. 브라우저가 자동 발행하는 요청까지 보호된다

이 시스템은 실시간 영상을 다룬다. `<video>`, `<img>` 태그나 WebSocket 핸드셰이크가
발생시키는 요청에는 `Authorization` 헤더를 붙일 수 없다. 쿠키는 브라우저가 자동으로
실어 보내므로 이런 요청도 동일한 인증 체계로 보호된다. 영상 리소스가 API가 아닌
정적 리소스 형태가 되더라도 보호 대상에서 누락되지 않는다.

### 5. 프레임워크의 기본 경로다

Spring Security는 세션 생성, 쿠키 발급, 세션 고정 공격 대응, CSRF 처리를 기본으로
제공한다. JWT는 필터를 직접 작성해야 한다. 직접 구현한 인증 필터는 검증되지 않은
코드이며, 이 규모의 프로젝트에서 감수할 이유가 없다.

### 로그인 응답을 JSON으로 하는 이유

프론트엔드 프레임워크가 아직 정해지지 않았다. 두 방향의 전환 비용이 다르다.

- JSON 응답 → 서버 렌더링 방식으로 전환: 거의 무비용
- form login의 302 리다이렉트 → SPA 대응으로 전환: 인증 응답 처리 전면 재작성

비용이 비대칭이므로 JSON이 안전한 기본값이다.

### AI 파이프라인에 인증을 두지 않는 이유

인증을 두 곳에 두면 계정과 세션을 이중으로 관리해야 한다. 사람이 접근하는 진입점은
Spring 하나뿐이므로, AI 파이프라인에 인증을 추가해도 실질적인 보안 이득이 없다.
대신 네트워크 계층에서 외부 접근을 차단한다.

## 트레이드오프

채택에 따라 감수하는 비용은 다음과 같다.

### 수평 확장 시 추가 작업이 필요하다

서버를 2대 이상으로 늘리면 세션 공유 수단이 필요하다. 인메모리 세션은 인스턴스
간에 공유되지 않으므로 로그인한 사용자가 다른 인스턴스로 라우팅되면 인증이 풀린다.
Spring Session + Redis 도입으로 해결되지만, 인프라 구성 요소가 하나 늘어난다.

### 서버가 메모리를 사용한다

세션 수에 비례해 서버 메모리를 소비한다. 사용자가 소수인 본 시스템에서는 무시할
수준이지만, 무상태 방식 대비 자원을 쓰는 것은 사실이다.

### CSRF 대응이 필요하다

쿠키는 브라우저가 자동 전송하므로 교차 사이트 요청 위조에 노출된다. 헤더 기반
토큰 방식은 구조적으로 이 문제가 약하다. `SameSite=Lax` 쿠키 속성과 Spring
Security의 CSRF 토큰으로 대응하며, 이는 구현 항목으로 관리한다.

### 절대 만료는 직접 구현해야 한다

유휴 만료는 서블릿 컨테이너가 기본 제공하지만, 절대 만료는 제공되지 않는다.
로그인 시각을 세션에 저장하고 필터에서 경과 시간을 검사하는 코드를 작성해야 한다.

### 프론트엔드가 다른 출처에 있으면 CORS 설정이 필요하다

SPA를 별도 개발 서버에서 구동하는 경우 `allowCredentials: true`를 포함한 CORS
설정이 필요하다. 포트만 다른 경우는 same-site로 취급되므로 `SameSite=Lax` 쿠키는
정상 동작한다.

## 재검토 조건

아래 중 하나라도 발생하면 이 결정을 다시 검토한다.

1. **서버 인스턴스가 2대 이상이 된다** — 먼저 Spring Session + Redis 도입을
   검토한다. 이 보완으로 해결되지 않는 상황에서만 JWT를 재고한다.
2. **브라우저가 아닌 클라이언트가 추가된다** — 모바일 앱이나 외부 시스템 연동이
   생기면 쿠키 전달이 자연스럽지 않다. 다만 이 경우에도 전면 교체가 아니라,
   해당 클라이언트에 한해 별도 인증 수단을 병행하는 방안을 먼저 검토한다.
3. **외부에 공개하는 API가 생긴다** — 제3자에게 제공하는 API는 세션 쿠키가
   적합하지 않다.
4. **세션 저장소가 병목이 된다** — 사용자 수가 예상을 크게 초과하는 경우.
   현재 시나리오에서는 발생 가능성이 낮다.

1번은 인프라 보완으로 해결되므로 재검토 결과가 JWT 전환으로 이어지지 않을 가능성이
높다. 2번과 3번은 요구사항 자체가 바뀌는 경우이며, 이때는 인증 방식 전체를 다시
설계한다.
